3) Describe your strategy for dealing with thruster failures

- Lander_Control and Safety_Override never touch Main/Left/Right_Thruster directly. They ask the agent for a world-oriented thrust(ax, ay) and RobustAgent figures out delivery with whatever's still alive. All three working means stay upright, use main plus the relevant side thruster normally. Lose one causes the ship to rotate onto whichever single remaining thruster needs the least turn (with THRUSTER_SWITCH_BIAS so we don't flip-flop between two options). 
If we lose a side thruster specifically, we tilt the main thruster to steal a sideways component instead, but capped so the tilt never lifts more than was actually asked for. We implemented boundaries on the map so that if the craft starts drifting toward the edge of the map, it automatically fires a thruster to push it back opposite the velocity before it can fly off.
If we lose the main thruster, our strategy is to hover low on a side thruster, then at DROP_HEIGHT (36px up) go upright and perform a controlled free-fall, scaled so impact speed stays under the landing limit with a buffer to spare.

6) Assume a human pilot was in charge of controlling the craft 
   (i.e. the pilot has control of thrusters and rotation).
   How would you change Safety_Override() so that it prevents
   the pilot from accidentally crashing the lander?
   
   - We'd actually keep the version we already designed for: it runs dead last, so whatever it commands is what physically happens regardless of what Lander_Control or a pilot asked for moments earlier, and we never lose control. This means we let the pilot fly freely while sensors are healthy, same as now (i,e, using cone checks, map-edge override, and the safe-landing box only step in near actual danger). 
   The moment a sensor goes blind on one axis, we reclaim only the controls we can no longer see the effect of on that axis (i.e. use side thrusters if the X sensors are gone, and main thruster if Y is gone) and re-issue our own last known command every frame, so an untracked pilot input can't quietly poison our predictions. And if the angle sensor dies, we refuse pilot rotation entirely, for an unlogged turn breaks the one thing (our Rotate history) everything else leans on. 
   If we actually had that shared variable set up, it would work a lot better than what we have. We would know exactly what the pilot did every frame instead of just guessing from drifted sensor readings, so our physics math would never get thrown off and we would not need to lock the pilot out of any controls at all. Basically, taking away the pilot's control is our "we can't see what you're doing, so we'll just do it ourselves" plan B, and if we could see it, we would not need a plan B.

9) Would you buy/drive a car that you know has control software
